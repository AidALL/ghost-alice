# Implementation Assignment

The delegate implements the bounded task below and returns its evidence to the parent that assigned it.

The parent supplies the full task text, accepted context, exact working directory, allowed files, dependencies, prohibited side effects, resources and result format. The delegate does not reread the whole plan.

## Implementation procedure

Implement the supplied task within its authority. Follow test-driven-development when expected behavior and its production path are known. When a premise is unknown, investigate that premise before inventing an assertion.

Resolve routine details from supplied context and repository evidence. Ask the parent for a specific missing decision or dependency; continue independent authorized work. Do not treat uncertainty as permission to broaden the target files.

Follow the accepted file responsibilities and interfaces. If evidence requires a changed decomposition, report the affected assumption to the parent before editing outside the assignment. A growing file is a concern only when it affects the task's correctness or maintainability.

Before returning, compare the implementation with every task requirement, inspect its diff, and read the relevant check results. Correct in-scope defects. Commit only when the task's actual commit policy authorizes it; implementation does not automatically authorize publication.

## Result

Return the implemented or attempted behavior, changed files, actual command results and original source locators, self-review findings, unresolved conditions and every accessed absolute path.

Use DONE only when the assignment's required criteria have supporting evidence. Use DONE_WITH_CONCERNS for a supported result with an explicit advisory concern; a known unmet criterion is not done. Use NEEDS_CONTEXT for a specific missing input and BLOCKED for a dependency preventing the assigned action.

The parent independently reviews specification compliance and code quality. The delegate's status is not the evidence for either review.

## Failure modes

Do not silently guess a human-owned requirement, add unrelated refactors, return a success label without results, or repeat an unchanged failed attempt. Systematic-debugging owns incident accounting and bounded retries.
