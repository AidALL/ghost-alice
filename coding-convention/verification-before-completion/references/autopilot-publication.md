# Autopilot Proof Publication

Core selects current-ready-owned execution units from the current response route, owner, work-unit ID and contract revision. AP records only their admitted execution criteria; cumulative history, unadmitted protections, missing route, planning and explanation do not create publication obligations. Applicability and recording availability are separate. The compatible Core-managed no-argument PreToolUse/Stop chain selects `autopilot-completion-receipt.v2`; direct legacy APIs retain their strict v1 default. Unknown Core capability reports incompatible or unavailable and never falls back to cumulative criteria. Do not create work or approval to activate recording.

Core first reconciles the current request with continuing authorized work. A bounded discussion without selected execution has no AP publication; executed read-only review/report and positive closure still require owner verification. Consume Core publication_route (`none`, `prepare`, `publish`, `blocked`) rather than infer applicability from a run or backlog. Missing/stale route blocks capture/advancement only.

## Managed v2 workflow

1. Use the actual installed pretool notice and current intake receipt. Its locations identify Core source APIs separately from runtime modules, ledger state, project and installed skills. Preserve the exact ledger root, platform and session; transport does not grant admission, native permission, origin or approval. For current selected units, the concrete `prepare_command` returned by AP binds the existing target receipt. The explicit helper form is `autopilot_completion.py prepare --intent-root ROOT --platform PLATFORM --session-id SESSION --input-event-id INPUT --schema-version autopilot-completion-receipt.v2` under the validated source/location environment. It records the current binding and returns unit-qualified criteria, receipt token, original capture time and publish command. It neither verifies business work nor requires `approved-run.json` or `tasks.jsonl` to exist. Keep each returned unit/revision separate.
2. For genuinely new business proof, perform the necessary check once after its prospective capture. Retain exact proof bytes, source locator and actual original verification time. Use the returned `publish_command` with the original supported `[completion-check]` on stdin and `--verified-at ORIGINAL_ISO_TIME`; keep its qualified criterion coverage unchanged. The helper checks proof consistency, not the truth of a caller-supplied time. A missing capture, ambiguous evidence or unavailable original source/time stays a specific recording gap; it is never repaired by relabelling old proof.
3. For accepted unchanged proof, use `autopilot_completion.py publish --receipt-token CURRENT_TOKEN --evidence-reference ORIGINAL_REFERENCE --schema-version autopilot-completion-receipt.v2` under the current returned target/source/location bindings. Repeat `--evidence-reference` for independent accepted records. Do not supply new proof bytes or a new verification time with reference reuse. A new input creates a current publication request while the original evidence record and source/time remain unchanged. A changed criterion definition, relevant artifact dependency or incompatible owner/target reopens only affected coverage; unrelated valid proof remains retained.
4. Publish before the first executed-work final closure claim when recording is applicable and available. Preparation and pending publication are bookkeeping evidence; the actual registered Stop adapter validates and applies the request in the owning Core transaction. They are not proof that business work succeeded. Preserve the requested business answer and its supported completion block. Core's delivery selector permits metadata-only repair only with a usable visible prior answer and unchanged claims; otherwise assemble the complete requested payload and corrected metadata.

## Original proof format

For new proof, preserve the supported completion block covering exactly the returned criteria, with exactly one nonempty top-level `- evidence:` section. The helper derives its exact reference text from that section; it does not substitute nested claim evidence or invent a tool identifier. Missing, empty, duplicate, placeholder, ambiguous or partial evidence stays rejected. Supply the original raw timestamp once through `--verified-at` without inserting it into proof that lacks a timestamp. If the proof declares `verified-at` or `verified_at`, its single value must match that raw string exactly; malformed, inconsistent or ambiguous declarations stay rejected. A deliberate legacy `--evidence-source` override must be nonempty and match the unchanged reference already in the proof. Publication checks consistency and preserves the unchanged proof digest; it does not independently authenticate an external result or a caller's first supplied timestamp.

## Recording-only recovery

A binding, source-provider or publication failure does not erase supported business evidence. Keep the original proof and its time; continue independent authorized work and use intake/binding repair tools. Publication and application remain blocked until recording is repaired. Make a bounded first repair with the original receipt/reference; an identical unchanged failure parks recording until a decision-relevant recording or dependency change. Do not rerun unchanged business verification merely to generate a later timestamp. If the selected contract or relevant artifact actually changed, verify only the affected condition. Report business status and recording status separately without a finalized completion check for unsupported claims. No fake origin, permission, admission, approval, run path or source-authority fallback is allowed. Use stdin or permitted runtime scratch when additional task files are prohibited.

## Explicit legacy path

Public callers that deliberately select v1 keep its generation-bound rules. Its preparation form is `prepare --reapprove-current-input --intent-root ROOT --platform PLATFORM --session-id SESSION --input-event-id INPUT`; publish uses its returned command, unchanged proof and original verification time. Proof must follow that original capture. Do not apply v1's generation admission or capture-time requirements to already accepted v2 reference reuse, and do not loosen v1 provenance checks to emulate v2.
