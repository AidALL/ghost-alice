# Autopilot Proof Publication

Core selects current-ready-owned execution units from the current response route, owner, work-unit ID and contract revision. AP records only their admitted execution criteria; cumulative history, unadmitted protections, missing route, planning and explanation do not create publication obligations. Applicability and recording availability are separate. The compatible Core-managed no-argument PreToolUse/Stop chain selects `autopilot-completion-receipt.v2`; direct APIs use the strict v1 default. Unknown Core capability reports incompatible or unavailable and never falls back to cumulative criteria. Do not create work or approval to activate recording.

Core first reconciles the current request with continuing authorized work. A bounded discussion without selected execution has no AP publication; executed read-only review/report and positive closure still require owner verification. Consume Core publication_route (`none`, `prepare`, `publish`, `blocked`) rather than infer applicability from a run or backlog. Missing/stale route blocks capture/advancement only.

## Original proof format

For new proof, preserve the supported completion block covering exactly the returned criteria, with exactly one nonempty top-level `- evidence:` section. The helper derives its exact reference text from that section; it does not substitute nested claim evidence or invent a tool identifier. Missing, empty, duplicate, placeholder, ambiguous or partial evidence stays rejected. Supply the original raw timestamp once through `--verified-at` without inserting it into proof that lacks a timestamp. If the proof declares `verified-at` or `verified_at`, its single value must match that raw string exactly; malformed, inconsistent or ambiguous declarations stay rejected. An explicit `--evidence-source` override must be nonempty and match the unchanged reference already in the proof. Publication checks consistency and preserves the unchanged proof digest; it does not independently authenticate an external result or a caller's first supplied timestamp.

## Recording-only recovery

A binding, source-provider or publication failure does not erase supported business evidence. Keep the original proof and its time; continue independent authorized work and use intake/binding repair tools. Publication and application remain blocked until recording is repaired. Make a bounded first repair with the original receipt/reference; an identical unchanged failure parks recording until a decision-relevant recording or dependency change. Do not rerun unchanged business verification merely to generate a later timestamp. If the selected contract or relevant artifact actually changed, verify only the affected condition. Report business status and recording status separately without a finalized completion check for unsupported claims. No fake origin, permission, admission, approval, run path or source-authority fallback is allowed. Use stdin or permitted runtime scratch when additional task files are prohibited.

## Explicit v1 path

Public callers that deliberately select v1 keep its generation-bound rules. Its preparation form is `prepare --reapprove-current-input --intent-root ROOT --platform PLATFORM --session-id SESSION --input-event-id INPUT`; publish uses its returned command, unchanged proof and original verification time. Proof must follow that original capture. Do not apply v1's generation admission or capture-time requirements to already accepted v2 reference reuse, and do not loosen v1 provenance checks to emulate v2.

## Repair limits and authority

Actual current and prior human instructions supply the authorization envelope: objective, prohibitions, allowed actions and targets, side effects and resources. Retained authority facts preserve their human source; trusted system/project constraints retain their identified source. Intake compresses semantic facts and the router selects current work without granting authority. Distinguish human-owned criteria and resource choices from agent-derived interpretations and bounded local plans; an absent explicit resource cap is not an approved human limit. Renew a narrower implementation contract only inside actual authority, without weakening acceptance criteria or inferring permission from focus expansion. Request an exact human-owned decision before crossing its boundary. Actual grant renews only the affected plan and granted scope; denial parks it; no response leaves it waiting. Continue other eligible authorized work.

A failed repair round requires a corrective change and a completed relevant observation of the same unresolved failure. Initial failure is zero. Group by unresolved failure, affected criterion, stage and target; explain what each result changes about cause, mapping, design or verification. Unknown causes cannot justify relabeling/reset, and identical error text cannot combine unrelated business and recording failures. Preserve cumulative attempts and the addressed first-five checkpoint across agents and handoffs. Demonstrated resolution followed by recurrence is a linked new incident. Five failed rounds is the maximum before the first mandatory premise reassessment, not a minimum retry count or whole-task limit. Once addressed, cumulative six or seven alone do not retrigger that checkpoint. New relevant contradiction or a current stopping condition can require reassessment. Continuation requires a distinguishable hypothesis, a discriminating check, an explicit additional-attempt or resource allowance and a stopping condition inside remaining parent resources. Reassessment resets neither attempts nor resources; exhaustion parks the affected continuation. Five alone does not require human escalation.

Retain decisions in existing work context and handoffs; no counter hook, classifier, compulsory per-conversation record or new mandatory report is required. Recording-specific typed recovery parks an identical unchanged failure without waiting for five rounds. Preserve known business proof when only recording fails. Exclude parked and human-waiting branches until an actual relevant reopening event. If no eligible work remains, use valid proof for all required criteria and resolve relevant contrary evidence before owning completion verification; otherwise report honest partial/waiting status.
