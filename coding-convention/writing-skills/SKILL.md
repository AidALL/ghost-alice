# Writing Skills

The response model changes reusable skill guidance from observed behavior or a direct source-contract contradiction, then validates the package and the affected decision. Read test-driven-development for executable changes; an instruction-only contradiction can use preserved source evidence instead of an invented failed delegate run.

## Baseline and scope

Before editing, identify the exact skill decision that is wrong or ambiguous. Retain the actual baseline outcome or source quotation and locator. A passing baseline stays a pass; a predicted failure is not an observed failure.

Write a reusable technique, pattern or reference when repeated work benefits from it. Keep one-off project rules in project instructions. Do not create a skill merely because a regular expression or existing automation can enforce the constraint.

Define the affected evaluation before editing. Include only cases whose outcomes can change the response model's judgment of an acceptance criterion or the next correction. For executable behavior, the response model follows test-driven-development for the code and test being changed.

## Author the package

Use `SKILL.md` for core guidance, conditionally loaded `references/` for detail, and `scripts/` for executable support. At an operational handoff, write enough for a reader without prior conversation to act: identify the caller and trigger, the authoritative origin and required shape of transferred values, the exposed tool or actual API/CLI invocation, the result and its storage owner, and the conditional next action. Distinguish the response model's meaning judgment from code that authenticates its recorded judgment. Put a shared procedure in one owning reference and link callers to its section; do not repeat this field list in every sentence or replace an executable transfer with an actor label. Mark illustrative prompts, schemas and data as examples rather than ambient task authority.

The frontmatter must contain a directory-matching lowercase-hyphen name and a description that states what the skill does and when it is used. The description serves discovery, not execution: it contains no summary of the body and no procedure step, and no point appears twice in it. Keep descriptions within 1024 characters with the key use case first; state compatibility when the workflow depends on an environment.

In the body, state the workflow's purpose, applicability, procedure, output and failure modes. Use a quick-reference table when the reader looks up an entry by its condition. Prefer one complete relevant example over multiple shallow language variants. Long code and reference tables belong in supporting files; every reference in the package needs a clear loading condition.

Do not add hypothetical defenses or repeat a prohibition merely to increase emphasis. If a real evaluation shows rationalization, revise the instruction that allowed the wrong decision.

## Validate and evaluate

1. Preserve baseline evidence before changing the candidate.
2. Edit the affected body, callers and references to remove the demonstrated contradiction.
3. Run the affected pressure, application or source-contract check required by the task and record the actual outcome and limits.
4. If an observation contradicts a requirement, follow the [diagnostic procedure](references/bulletproofing-skills.md#procedure) to select and apply the justified correction, then repeat only the affected checks.
5. Distribute or commit only under the human user's existing authorization and after required validation succeeds.

Coordinated changes may span packages; each changed package still needs its own disposition.

Verification-before-completion defines useful-check selection, evidence reuse, original source and time, and completion claims. Systematic-debugging defines incident accounting and bounded continuation. Do not duplicate either policy in a skill under repair.

## Failure modes

- Do not backdate missing baseline evidence or delete inconvenient results.
- Do not add a new report, hook or mandatory record when existing task context already preserves the evidence.
