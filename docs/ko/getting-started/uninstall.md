# 설치 제거 절차

[🇺🇸 English](../../getting-started/uninstall.md) | [🇰🇷 한국어](./uninstall.md)

제거 명령은 인스톨러가 작성한 `install-state` 매니페스트를 읽습니다. 인스톨러가 설치하거나 변경했다고 기록한 항목만 제거하거나 복원합니다.

## 제거 범위 선택

| 목표 | 실행 명령 | 참고 |
| --- | --- | --- |
| Ghost-ALICE 관리 대상 전체 제거 | `bash install.sh --uninstall` | 기록된 대상 전체를 제거합니다 |
| 한 플랫폼 제거 | `bash install.sh --platform codex --uninstall` | 다른 플랫폼의 설치는 유지합니다 |
| 선택한 스킬 제거 | `bash install.sh --platform codex --uninstall task-router` | 다른 스킬이 남으면 훅과 공유 파일을 유지합니다 |
| 애드온 하나 제거, Core 유지 | `bash install.sh --platform codex --uninstall --addon <addon-id>` | 애드온의 훅을 먼저 해제하고 검증된 전용 파일을 제거합니다 |

개별 애드온 제거와 선택한 스킬 제거는 범위가 다릅니다. Core 갱신은 기존 애드온을 유지하며, 명시적인 애드온 제거 명령이 제거 범위를 선택합니다. 전체 제거는 설치된 애드온의 부속 기록을 포함한 활성 관리 대상을 정리하면서 필요한 복구 사본과 로컬 근거는 보존합니다. 개별 애드온을 제거하면 Core와 다른 애드온의 설치는 유지합니다. 선택한 스킬을 제거할 때는 기존 의존성 확인이 설치된 애드온에 필요한 Core 스킬을 보호합니다.

## 기본 명령

플랫폼을 지정하지 않으면 제거 명령이 관리 대상 전체를 제거합니다.

```bash
bash install.sh --uninstall
```

```cmd
.\install.cmd --uninstall
```

플랫폼을 지정하면 제거 명령이 해당 플랫폼의 관리 대상만 제거합니다.

```bash
bash install.sh --platform codex --uninstall
```

```cmd
.\install.cmd --platform codex --uninstall
```

특정 스킬만 제거하려면 플랫폼과 스킬 이름을 함께 지정해 주세요. 다른 Ghost-ALICE 스킬이 남아 있으면 제거 명령은 훅과 `_shared`를 유지합니다.

선택 제거는 제품군 이름을 실제 하위 스킬로 확장하고 제품군과 각 하위 스킬의 의존성을 함께 확인합니다. 언인스톨러는 요청된 대상을 분류하고, 물리 삭제가 서비스에 영향을 줄 때만 게이트웨이 담당 모듈에 해제를 요청합니다. 발견 경로의 스킬을 제거해도 독립 게이트웨이 런타임은 실행 상태를 유지합니다. 요청한 호스트에 Core 스킬이 남지 않으면 파일 삭제 전에 Core 훅을 해제하고 저장된 설정을 확인합니다. 소유 근거를 다시 확인하여 제거 가능한 파일을 삭제하거나 해당 호스트의 확인된 공유 참조를 해제한 뒤 [제거 기록](../reference/installer-architecture.md#제거-기록)을 갱신합니다. 다른 호스트가 보존한 파일은 요청한 호스트에 남은 Core로 세지 않으며, 소유 근거를 확인하지 못한 파일은 남은 대상으로 셉니다. Core 스킬이 남지 않을 때만 부트스트랩을 제거하고, 아래 전체 제거에서 다루는 지원 기록은 보존합니다. 해제 뒤 실패한 경우는 [복구 원칙](#복구-원칙)을 확인해 주세요.

```bash
bash install.sh --platform codex --uninstall task-router
```

```cmd
.\install.cmd --platform codex --uninstall task-router
```

## 기준 파일

인스톨러는 플랫폼별 매니페스트를 다음 위치에 기록합니다.

- `~/.ghost-alice/install-state/claude.json`
- `~/.ghost-alice/install-state/codex.json`

언인스톨러는 매니페스트의 `targets`와 `system_env_changes`를 조회합니다. 매니페스트가 없거나 손상되었다면 인간 사용자가 검토하도록 알리고, 삭제 대상이 될 지원 기록과 복구 자료를 보존합니다. 독립적인 훅 정리는 자체 결과를 보고하며, 그 결과가 매니페스트 대상의 제거까지 입증하지는 않습니다.

## 제거 순서

전체 제거는 선택한 플랫폼마다 다음 단계를 순서대로 실행합니다.

1. 명령 시작 시점의 JSON·TOML 설정 바이트를 보존하고, 각 담당 모듈이 분류한 대상으로 하나의 제거 항목 목록을 만듭니다. 설정이나 파일을 변경하기 전에 기존 잠금을 획득하여 게이트웨이의 제거 조건을 확인합니다. 이 확인 단계는 서비스를 중지하거나 서비스 설정을 해제하지 않습니다.
2. 유효한 권한 변경 보류 기록이 있으면 그 기록의 담당 모듈이 원래 스킬 이름 범위의 변경을 먼저 완료합니다. 그다음 다른 담당 모듈의 설정 변경을 적용합니다. 애드온과 Core의 소유한 등록을 해제하며, Core 권한 기록기와 훅 편집기는 같은 설정 후보를 한 번 저장합니다. 권한 규칙의 소유 근거를 확인하지 못하면 그 규칙을 보존하며, 별도 근거가 있는 훅이나 파일까지 소유 불명으로 판정하지 않습니다.
3. 훅 해제 시도 뒤 실제 훅 설정을 조회합니다. 해제를 확인하지 못한 훅이 참조하는 스킬·런타임·재시도 기록은 같은 제거 항목 목록에서 보존 대상으로 변경합니다. 의존 파일을 보존한 결과를 제거 성공으로 표시하지 않습니다. 독립 항목을 계속 제거할 수 있더라도 설정 저장·조회 오류는 오류로 남깁니다. 그다음 기록된 조건에 따라 Codex 기능·프로젝트 신뢰 설정을 복원합니다.
4. 언인스톨러가 최종 제거 루트와 Codex 전체 제거 요청 여부를 `installer.gateway_participant.removal`에 전달합니다. 이 참여자가 언인스톨러의 파일 삭제 전에 등록된 문맥 게이트웨이를 분리할지 판정합니다. 설치 기록의 `service` 섹션이 서비스 파일을 지정합니다. 서비스 부재를 확인한 뒤 소유한 launch agent와 provider 블록을 제거하고 `service` 섹션을 삭제하며, 주변의 현재 사용자 설정, 상태 디렉터리, 구성 요소 로그와 기존 복구 자료는 유지합니다. Codex 구성이나 게이트웨이 서비스·상태 파일 자체가 심볼릭 링크이거나, 서비스 파일이 인스톨러 밖에서 변경되었거나, 해제 결과를 확인할 수 없으면 뒤따르는 Core 제거 작업을 실패로 중단합니다. 런타임·서비스 파일을 유지하고 Codex 연결 해제를 요청하지 않은 제거는 게이트웨이를 실행 상태로 유지합니다. 링크는 가리키는 곳이 아니라 링크 자신의 경로로 판정합니다. `service` 섹션이 없으면 제거는 launchd에 조회하며, 적재된 게이트웨이 서비스의 프로그램이 제거 루트 안이면 검토를 위해 제거를 중지합니다.
5. 남은 대상 항목을 적용하기 직전에 소유 근거를 다시 확인합니다. 허용된 루트 안에서 관리 소유를 확인한 대상만 제거합니다. 다른 호스트의 설치 목록·현재 배치·애드온 기록에 유효한 참조가 있으면 공유 파일을 보존하고 요청한 호스트의 참조만 해제합니다. 확인된 결과마다 [기록 담당자](../reference/installer-architecture.md#제거-기록)에 전달하며, 실패한 대상의 재실행 근거는 지원 자료 정리 전에 보존합니다.
6. Codex 부트스트랩 또는 전역 규칙의 관리 블록을 제거하면서 Ghost-ALICE가 관리하지 않는 항목을 유지합니다. 소스 저장소의 공용 `core.hooksPath`는 마지막 호스트의 전체 제거에서만 복원합니다. 지금 값이 install-state가 설치가 작성했다고 기록한 값과 같을 때만, install-state가 기록한 설치 전의 값을 다시 작성합니다(설치 전 값이 없으면 설정을 삭제합니다). 다른 호스트의 install-state가 남아 있으면 그 호스트를 위해 값을 그대로 두고, 기록이 없는 값이나 설치 뒤에 바뀐 값도 그대로 둡니다.
7. 남은 복구 자료를 보존하기 전에 [최종 정리 담당자](../reference/installer-architecture.md#폐기와-최종-정리)가 불필요하다고 확인한 이전 사본을 삭제하도록 요청합니다. 선택한 플랫폼의 병합 대기 원본을 보존한 뒤 활성 대기열을 제거하되, 미완료 제거에 필요한 대기열은 유지합니다. 다른 호스트가 사용하는 공용 복구 사본도 유지합니다. 보존 사본은 `~/.ghost-alice/uninstall-backup/<platform>/support-state/` 아래 새 디렉터리에 저장하며 보고서에 `backup_path`로 표시합니다. 최상위·내부 링크를 포함해 원래 수정 시각과 심볼릭 링크 표현을 유지합니다. 링크 시각을 보존할 수 없거나 복구 자료에 Windows junction이 있으면 원본 루트와 설치 상태 매니페스트를 검토 대상으로 남깁니다.
8. 재실행에 더 필요하지 않은 지원 기록만 삭제합니다. 앞선 기록 정리와 복구 사본 보존이 성공할 때까지 설치 상태 매니페스트를 유지합니다. 설정이나 소스 저장소의 Git 훅 경로 복원에 실패한 경우에도 해당 변경 기록과 매니페스트를 보존합니다. 결과 보고서는 `~/.ghost-alice/uninstall-reports/` 아래에 작성합니다. 이 폴더에 남기는 보고서 수는 [런타임 상태 보존](../reference/repository-structure.md#런타임-상태-보존)이 정합니다.

제거 명령은 보존 사본 디렉터리, 최근 제거 보고서, 소스 체크아웃, 대화·세션 근거, 의도 원장과 `~/.ghost-alice/secrets.env` 같은 개인정보를 담은 로컬 파일을 삭제하지 않습니다. 영구 보존한다는 뜻은 아닙니다. Ghost-ALICE가 설치되어 있는 동안에는 [런타임 상태 보존](../reference/repository-structure.md#런타임-상태-보존) 규칙이 이 자료에 따로 적용됩니다. 설치 기록 `~/.ghost-alice/installed-payload.json`과 `~/.ghost-alice/rollbacks/` 아래의 배치 폴더는 두 호스트가 공유합니다. 한 호스트의 전체 제거는 다른 호스트를 위해 둘을 남깁니다(`manual-review`, `shared-support-in-use-by-other-platform`). 마지막 호스트의 전체 언인스톨러는 [완료 배치 정리 담당자](../reference/installer-architecture.md#설치에-성공한-코드-버전)에게 불필요한 관리 원본 삭제를 요청한 뒤, 남은 배치 복구 자료를 `~/.ghost-alice/uninstall-backup/<platform>/support-state/`에 보존하고 두 활성 경로를 제거합니다. `~/.ghost-alice/io-trace.jsonl` 같은 실행 감사 기록은 설치 대상이 아니라 로컬 감사 기록입니다. 실행 연결을 제거해도 자료 전체를 삭제하지는 않습니다. 이 설정·파일 결과만으로는 실행 중인 호스트가 변경을 적용했는지, 이미 전달된 작업이 취소됐는지 확인하지 않습니다.

마지막 호스트를 전체 제거한 뒤에도 언인스톨러는 `~/.ghost-alice/versions/`의 코드 보관본을 유지합니다. 이후 전체 Core 설치를 실행하면 인스톨러가 [성공 코드 버전 보존 기준](../reference/installer-architecture.md#설치에-성공한-코드-버전)에 따라 이전 보관본을 정리합니다. 언인스톨러는 이 버전 정리를 실행하지 않습니다.

## 복구 원칙

정리 보고서를 읽을 때 스키마 버전 `2`, `mode=apply`, `<platform>-apply-<stamp>.json`은 제거를 적용한 실행의 출력으로 해석해 주세요. 과거 버전 `1` 보고서는 같은 실행 모드에 `mode=confirm`과 `<platform>-confirm-<stamp>.json`을 사용했습니다. 어느 이름도 인간 사용자의 확인을 기록하지 않습니다. 독립 정리 CLI는 `--apply`를 사용하고 `--confirm`을 별칭으로 계속 받습니다. 둘 다 없으면 설치·설정·복구 자료를 변경하지 않고 미리 보기 보고서를 작성합니다. 애드온 제거는 기본으로 적용하며, `--dry-run`이 두 적용 별칭보다 우선합니다.

현재 분류기는 관리 대상에 외부 변경이 있으면 `externally-modified-managed`를 기록합니다. 외부 변경은 설치 뒤 인스톨러가 찾은, 인스톨러의 기록에 없는 변경이며 인스톨러는 변경한 주체를 기록하지 않습니다. 관리 기록이 항목을 소유하지 않으면 `unclaimed`를 기록하며, 이 상태는 삭제를 허용하지 않습니다. 과거 보고서나 병합 대기 항목을 읽을 때 `user-modified-managed`는 `externally-modified-managed`, `user-owned`와 진단의 `owner=user`는 `unclaimed`, `user-modified-purge`는 `external-change-purge`, `user-modified-quarantine`는 `external-change-quarantine`, `retired-managed-user-changes-preserved`는 `retired-managed-external-changes-preserved`로 해석해 주세요. 이 이름들은 분류와 보존 상태를 나타내며 변경한 주체를 뜻하지 않습니다. 현재 이름으로 바꾸기 위해 과거 항목, 백업 경로, 해시나 기록된 결과를 재작성하지 마세요. 언인스톨러와 진단 명령은 현재 대상을 다시 분류합니다.

개별 애드온 제거는 파일을 삭제하기 전에 인스톨러가 Claude Code 설정에 추가한 `Skill(...)` 허용 규칙과 Codex의 소유한 훅 신뢰 설정을 해제합니다. 인스톨러의 Claude Code 허용 규칙 소유권은 설정 파일과 매니페스트가 선택한 스킬 이름에 결합됩니다. 기존 규칙, 이 인스톨러가 추가하지 않은 나중의 중복 규칙과 소유권을 모르는 이전 규칙은 보호합니다. Codex의 남은 훅 신뢰 항목은 같은 명령이 반복돼도 각 훅의 실제 그룹·핸들러 위치를 따릅니다. 인스톨러는 Ghost-ALICE가 설치하지 않은 훅의 신뢰 항목과 그 필드·주석을 보존하며, 작성한 주체를 기록하지 않습니다. 대상 위치의 충돌을 해결할 수 없으면 제거를 중단합니다. 설정 작성기가 `.bak`를 만들 때는 애드온·Core·게이트웨이 변경을 포함한 전체 언인스톨 명령 시작 시점의 바이트를 사용합니다. 각 작성기가 자기 저장 실패를 복구할 때는 그 저장 직전의 상태를 복원합니다. 설정 저장은 심볼릭 링크를 유지하고 원자적으로 교체합니다. 이어지는 훅 설정 저장이 실패하면 원래 신뢰 설정의 내용과 수정 시각을 복구합니다. 복구 자체가 실패할 경우에도 원래 설정의 보존 사본을 남깁니다.

인스톨러의 Claude 권한 기록 작성기는 `addon-permissions/claude-v2.json`(스키마 `2`)에 귀속 기록을 저장합니다. 이 파일에서 인스톨러가 추가한 Core 규칙과 애드온 규칙을 구분합니다. 훅 전체 제거는 기록된 Core 추가 규칙을 하나씩 제거한 뒤 해당 제거 기록을 폐기합니다. 설치 전 규칙, 나중에 추가된 중복 규칙과 추가 기록이 없는 과거 Core 규칙은 보존합니다. 마지막 경우에는 보존한 규칙의 이름을 경고로 표시합니다. 작성기는 선택적 Core 필드가 없는 애드온 기록도 조회합니다. 이 추가 필드를 거부하는 구형 스키마 2 reader는 새 기록으로 규칙을 제거하지 못하며, 규칙을 삭제하는 대신 오류를 보고합니다.

새 권한 기록이 없으면 작성기는 이전 `claude.json` 기록을 조회합니다. 저장할 때는 새 귀속 기록을 임시 파일에 준비하고, 이전 기록이 있으면 고유한 `claude-v1-*.bak` 이름으로 이동한 다음, 마지막 파일 작업으로 활성 v2 기록을 교체합니다. 귀속 기록이 비었으면 활성 기록을 삭제합니다. 마지막 작업이 실패하면 이전 기록을 복원하며, 복원도 실패하면 백업을 보존하고 두 오류를 보고합니다. 언인스톨러는 규칙을 제거하기 전에 제거 대기 상태의 지문을 기록합니다. 언인스톨러가 설정을 저장한 뒤 귀속 기록 저장에 실패하면, 다음 제거 시도에서 설정 지문으로 이미 적용된 변경을 식별하고 다른 중복 규칙을 제거하지 않은 채 귀속 기록 저장만 마칩니다. 현재 설정 지문이 제거 전후의 지문 중 어느 것과도 일치하지 않으면 언인스톨러가 검토 대상으로 남깁니다.

`claude.json`만 읽는 구버전 언인스톨러는 `claude-v2.json`에 기록된 소유권을 사용하지 못합니다. 전환이 성공하여 이전 파일이 백업으로 이동한 뒤, 소유권 근거가 없는 애드온 허용 규칙이 남아 있으면 구버전 언인스톨러는 그 규칙을 보존하고 `manual-review`로 표시합니다. 이때 애드온 파일을 제거하기 전에 `partial`을 반환합니다. 구버전 인스톨러로 애드온을 다시 설치하면 `claude.json`을 다시 생성하고 남아 있는 규칙을 기존 규칙(`False`)으로 분류할 수 있습니다. 이후 구버전 언인스톨러는 그 규칙을 `preserved-existing`으로 보존하면서 다른 제거 조건이 충족된 애드온 파일을 제거할 수 있습니다. 따라서 구버전 언인스톨러의 파일 제거 결과만으로 v2 기록이 귀속한 권한까지 제거됐다고 판단할 수 없습니다. 구버전 코드로 되돌릴 때의 별도 의도 원장 제약은 [플랫폼별 업데이트 동작](./installation.md#플랫폼별-업데이트-동작)을 확인해 주세요.

애드온 제거 CLI는 오류나 부분 제거에 종료 코드 `2`를 반환하며, 중단된 제거의 재개 오류도 포함합니다. 종료 코드 `1`은 애드온을 찾지 못한 경우입니다. 수정된 대상의 보존, 불명확한 권한 소유권이나 설정 오류를 완전한 제거로 계산하지 않습니다.

훅이나 관련 서비스를 해제한 뒤 소유 재확인·파일 삭제·기록 정리가 실패하면, 언인스톨러는 성공한 해제를 유지합니다. 남은 파일, 이미 삭제되어 없는 파일과 정리가 필요한 기록을 구분해 보고하고 재실행 근거를 보존하며 0이 아닌 종료 코드를 반환합니다. 애드온 제거 결과의 `unknown`은 언인스톨러가 파일 상태를 조회하지 못했다는 뜻이며, 파일을 삭제했다는 뜻이 아닙니다. 표시된 원인을 해결한 뒤 같은 제거 명령을 다시 실행해 주세요. 언인스톨러는 현재 상태를 확인하고 남은 삭제나 기록 정리를 마치며, 자동으로 재설치하거나 연결을 복구하지 않습니다. 파일 삭제만으로 제거 완료를 판단하지 않습니다.

전체 제거는 권한 소유 근거 검토만 남았을 때 종료 코드 `0`을 반환합니다. 이때 언인스톨러는 해당 권한, 보존한 애드온 파일, 그 애드온의 의존 목록에 명시된 Core 파일을 보존합니다. 별도의 소유 근거가 있는 대상은 제거하고 `partial: permissions retained for review`를 표시합니다. 확인된 공유 참조나 보존하기로 한 사용자 자료도 유지하며, 이 자료가 남아 있다는 사실만으로 필요한 삭제의 실패로 판정하지 않습니다. 외부에서 수정한 애드온 대상이 남거나 실제 설정·Git 복원·게이트웨이 오류, 필요한 정리의 실패가 발생하면 0이 아닌 종료 코드를 반환합니다. 전체 제거의 권한 보존 예외가 애드온 제거 CLI의 종료 코드 규칙을 바꾸지는 않습니다.

- 다른 호스트의 유효한 참조가 있는 공유 파일은 보존하면서 요청한 호스트의 참조를 해제합니다.
- 없는 파일과 이미 정리된 설정은 `missing` 또는 `unchanged`로 보고하며, 남은 기록 정리는 끝까지 수행합니다.

## system_env_changes

`system_env_changes`는 인스톨러가 적용한 환경 변경 목록입니다. 제거 명령은 항목에 `before`/`after` 값이나 복원 메타데이터가 있을 때만 해당 변경을 복원합니다.

인스톨러는 `source_repo_hook_path`, `codex_hooks_feature_flag`, `codex_project_trust` 변경을 기록합니다. 각 변경의 담당 함수는 기록된 복원 조건을 확인합니다. 담당 함수는 현재 설정값이 설치 직후의 기록값과 같은 경우에만 이전 값을 복원하고, 다른 현재 값은 보존합니다. 설정 조회나 문법 오류가 있으면 변경 기록을 보존하고 오류를 알립니다.

개발자는 새 `kind`를 추가할 때 `installer_update/install_state_schema.md`를 먼저 갱신하고 설치 기록과 제거 복원 테스트를 모두 추가합니다.
